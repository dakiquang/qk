[review comment](https://github.com/pypa/pip/pull/13535#discussion_r3523647331) states exactly:

> no devnull guard on the write side, so `PIP_CONFIG_FILE=/dev/null pip config set ...` now exits 0 and drops the value.

Defective range: [src/pip/_internal/configuration.py:379–392](https://github.com/pypa/pip/blob/ca887570a89a727deb62f97fc4d3436b81c5f0fc/src/pip/_internal/configuration.py#L379-L392). The fallback opens whatever `PIP_CONFIG_FILE` names without rejecting `os.devnull`.

Fixed range: [src/pip/_internal/configuration.py:394–405](https://github.com/pypa/pip/blob/8aa4aa764c1fe165b1d0c1e7f463192e01159c5e/src/pip/_internal/configuration.py#L394-L405). ### Core defect B: parser stored in the wrong scope, losing reuse

[review comment](https://github.com/pypa/pip/pull/13535#discussion_r3523650997) states exactly:

> I think this should be append to `_parsers[self.load_only]`, not `_parsers[kinds.ENV]`, or it's not re-entrant.

Defective range: [src/pip/_internal/configuration.py:379–392](https://github.com/pypa/pip/blob/ca887570a89a727deb62f97fc4d3436b81c5f0fc/src/pip/_internal/configuration.py#L379-L392). `_get_parser_to_modify` looks in `_parsers[self.load_only]` but appends the newly created parser to `_parsers[kinds.ENV]`. A second modification on the same `Configuration` object therefore misses its first parser and reconstructs another. **Source-derived consequence:** when changes have not yet been saved, separate parser snapshots can overwrite rather than preserve the preceding pending change. That consequence is an inference from parser construction and the save loop, not an additional quotation or an executed experiment.

Fixed range: [src/pip/_internal/configuration.py:394–405](https://github.com/pypa/pip/blob/8aa4aa764c1fe165b1d0c1e7f463192e01159c5e/src/pip/_internal/configuration.py#L394-L405). This is a state correctness fix, not merely a preference about container naming. No dedicated reentrancy regression test was found among this PR's added functional tests.

### Defect A: text-only `StringIO` is treated as a binary stream

[review comment](https://github.com/pallets/click/pull/1572#discussion_r3164813519) states:

> `get_pager_file`'s stream-wrapping logic can't correctly handle `io.StringIO` (used when no stdio streams are attached, or in the cmd-not-found fallbacks). `StringIO` has no `.buffer` and no `.encoding`, so it will take the “BinaryIO” branch and attempt to wrap a text stream in `io.TextIOWrapper`, which will raise a `TypeError`.

Defective range: [src/click/_termui_impl.py:419–429](https://github.com/pallets/click/blob/9cbbf10782d555d6995ef8969276d6a89792bc0c/src/click/_termui_impl.py#L419-L429). Fixed range: [src/click/_termui_impl.py:436–449](https://github.com/pallets/click/blob/1aa2d53d63ff68bf14b35931177aac9270e39713/src/click/_termui_impl.py#L436-L449) plus its buffer-capability helper at lines 35–47. Fixing commit: [`1aa2d53d63ff68bf14b35931177aac9270e39713`](https://github.com/pallets/click/commit/1aa2d53d63ff68bf14b35931177aac9270e39713), in merged direct follow-up [pallets/click#3405](https://github.com/pallets/click/pull/3405) (“`click.get_pager_file`: add tests (#1572 followup)”, merged 2026-05-16). It distinguishes buffered text streams and yields text-only streams without a binary wrapper.

The comment additionally claims that `StringIO` cannot accept arbitrary attributes. That assertion is **not adopted or counted**; the verified issue is the binary wrapping path.

### Defect B: temporary wrapper can close borrowed stdout

[review comment](https://github.com/pallets/click/pull/1572#discussion_r3164813497) states:

> `MaybeStripAnsi` subclasses `io.TextIOWrapper` directly and doesn't implement the non-closing behavior Click uses elsewhere (`_NonClosingTextIOWrapper.__del__` detaches to avoid closing shared global streams).

It explicitly reports that short-lived wrappers around `sys.stdout.buffer` can close the shared stream during garbage collection and break subsequent output.
